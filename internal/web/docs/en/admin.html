Users, invitations and settings

Administrators manage accounts and the server's rules. They have a vault like everyone else — and, like everyone else, cannot read other users' vaults.

Roles

RoleMay
Useruse an own vault
Administratoralso invite and manage users, read the audit log and change the settings

Inviting users

Accounts are made only by invitation. Under Users → Invite a user enter the e-mail address and the role. PassZit shows the invitation link once; send it to the person. The link works once and for the number of days in Sign-in and security (7 by default). The invited person chooses the master password and sets up two-factor sign-in. Open invitations can be withdrawn.

Managing users

  • Disable a user to stop all sign-ins at once (open sessions end). Enabling again restores everything.
  • Reset two-factor sign-in for a user who lost the phone and the recovery codes.
  • Delete the account removes the user with the personal vault for good — type the address to confirm.

Administrators cannot see or reset master passwords. A user who forgot it and has no recovery key can only start over with an empty vault: delete the account and invite again. The user list shows who has made a recovery key.

Vault policy

  • Lock the vault after inactivity (0 by default: it stays open until the user locks it or closes the browser) and clear copied passwords (30 seconds) — users may choose shorter times, and a lock time of their own when it is 0.
  • Minimum master password length (12) for new accounts and changed passwords.
  • Empty the trash after a number of days (30).
  • Former passwords kept per item (10): the length of the password history; former passwords can be shown and restored.
  • Files: the largest attached file (10 MB) and the storage for files per user (500 MB). Files are encrypted in the browser; the server cannot read them.
  • Sharing and export: only administrators make shared vaults; no exports (the web vault and the extension offer none — anyone who can open an item can still copy it).
  • Breach check (off by default): lets users compare their passwords with the Have I Been Pwned list. The server then asks api.pwnedpasswords.com with a five-character hash prefix and padding — it needs internet access for it, and neither side learns a password.
  • Key derivation (Argon2id): memory, passes and lanes. Stronger settings make stolen data harder to attack but every unlock slower; accounts move to new settings at their next unlock.

Sign-in and security

Session length and inactivity timeout, how many failed sign-ins block an address and for how long (doubling for repeated blocks), and how long invitations work. Blocked addresses can be released here or on the server with passzit-server --unblock-ip ADDRESS.

Network and access

The listen address, the networks allowed to connect (others are refused before TLS) and the public address used in invitation links. If you lock yourself out, run passzit-server --reset-allowlist on the server.

Certificate

A fresh server uses its own self-signed certificate: browsers warn about it once, and the browser extensions cannot connect to such a server. Under Settings → Certificate give it one that browsers trust:

  • Upload a certificate — from your company CA or bought — as PEM with the intermediate certificates, and its private key. It may also be for an IP address.
  • Let's Encrypt — free, renewed by itself 30 days before it expires. It needs a public DNS name for the server. Let's Encrypt checks the name either over port 80 of this server (reachable from the internet) or through a DNS record at Cloudflare — that also works for servers only in your network: create a Cloudflare API token with Zone → DNS → Edit for the zone; PassZit stores it encrypted.

The certificate is used at once on the console port, without a restart. Serve port 80 sends browsers that type the name without HTTPS to the console. The DNS of your network must point the name to this server. Back to the self-signed certificate: choose The console's own certificate.

If a certificate locks you out of the console (wrong name, expired), go back to the self-signed one on the server: in the appliance's setup menu Certificate, or sudo runuser -u passzit -- sh -c 'set -a; . /etc/passzit/server.env; passzit-server -data-dir /var/lib/passzit --certificate self' and restart the service. --certificate info shows the current one.

E-mail

Under Settings → E-mail enter an SMTP server (STARTTLS on port 587 or TLS on 465; the password is stored encrypted and is sent only over an encrypted connection), the sender address and the administrators' addresses. Send a test message to me checks it.

  • Administrators get notices about the server: a Let's Encrypt certificate that was not renewed, an uploaded certificate that expires within 21 days (once a day), a failed console backup or backup copy, and a change that waits for a second administrator (four-eyes principle).
  • Users get mail about what concerns them, in their own language: an invitation (when you tick Also send the invitation by e-mail), and emergency access that was requested, approved or rejected.

Messages say only what happened and link to the console; they never contain passwords or other secrets. A message that cannot be sent is noted in the audit log.

Audit log

Sign-ins, failed attempts, blocks, invitations, user changes, settings, master-password changes and recovery are recorded with time, user and address. Every entry contains a hash of the previous one; the page shows whether the chain is intact. The log never contains passwords or item contents.

Console backup

Daily, always encrypted backups of the whole server with an optional copy to an SFTP folder; download, delete and restore are described in Installing the server. Every backup, download and change is in the audit log.

Updates and server

New versions (only signed releases), the update channel (Stable or Testing), automatic installation in a chosen hour, the time zone and a restart of the service. On the appliance the server's network is set here as well. Details: Installing the server.

Groups

Under Groups administrators make groups and choose their members; vault managers then give a group access to a shared vault. See Shared vaults and groups.

Company sign-in

Settings → Company sign-in connects PassZit with the company's accounts. The master password always stays — it is the key to the vault; these add who may sign in: An e-mail address that the identity provider marks as not confirmed is refused. Single sign-on required applies to the web vault; to stop extension and command-line sign-ins of a person, disable the user in PassZit or use the directory (LDAP).

  • Single sign-on with OpenID Connect (Microsoft Entra ID, Google, Okta, Keycloak …) or SAML 2.0 (ADFS, Entra ID, Okta …). The sign-in page shows Sign in with …; the identity provider confirms the address, then the user enters the master password. Without Also ask for PassZit's own second factor the identity provider's sign-in replaces the authenticator code. Users must sign in through the identity provider stops people who were disabled there (administrators can always sign in, so a broken provider does not lock everyone out). Accounts still come only by invitation.
  • Active Directory / LDAP: at every sign-in (also of extensions) PassZit looks the address up with a service account; missing or disabled accounts cannot sign in. Look up tests the settings with an address.
  • Both can keep PassZit groups in step with company groups of the same name at every sign-in.

Browser extensions cannot use single sign-on; they sign in with the master password and the authenticator code (and are checked against the directory).

Four-eyes principle

With Settings → Vault policy → Four-eyes principle, sensitive actions of an administrator wait under Approvals until a second administrator approves them: deleting a user, resetting a second factor, making or inviting an administrator, and changing the vault policy, sign-in and security, network and company sign-in settings. Requests end after 24 hours; nobody approves their own. The stored request is sealed with the server key (it can contain secrets) and runs as the approving administrator; both are in the audit log. It takes effect with at least two active administrators — turning it off needs an approval too.

Taking the administrator role from an administrator or disabling one waits for approval too, so the rule cannot be switched off by reducing the administrators to one. Nobody approves their own request.
